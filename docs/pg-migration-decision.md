# KRTaker — SQLite → PostgreSQL migration decision

Status: **DECIDED (2026-08-09)** — migrate when trigger fires; path already validated.
Author: AJ for Kabir. Supersedes "when, not if" ambiguity with hard numbers.

## Current state (facts)
- API: PHP 8.x + SQLite 3.37.2, WAL + busy_timeout 15s + synchronous=NORMAL on
  shared cPanel (FTP-only, no SSH).
- Migration tooling ALREADY VALIDATED end-to-end (2026-08-02) against the real
  production export: `tools/pg_import.py` + `docs/pg-migration.sql` (23 tables,
  RLS policies, roles, idempotent ON CONFLICT). Every gotcha documented
  (IDENTITY vs GENERATED BY DEFAULT, psycopg list→array, FORCE RLS default-deny,
  reserved words, /root 700 traversal, no-DROP guard).
- PG target: NOT the cPanel host (ships pdo_pgsql, no PG server — 5432 refused).
  Target is a VPS (Lightsail 18.142.98.150 or new). VPS execution currently
  blocked on SSH access (needs box pubkey or Lightsail .pem).
- PostgreSQL-MIGRATION-NOTES reference: `references/pg-migration.md` + `docs/pg-migration.sql`.

## Decision: migrate when ANY of these triggers fires
1. **Concurrency**: SQLite write-lock contention in prod (busy_timeout 15s
   exceeded → 500 "database is locked") more than 3× in a week, OR
2. **Scale**: >500 active tenant orgs OR >5k units, OR
3. **Platform**: any requirement that needs PG (PostGIS, real FTS with ranking,
   a second app instance writing concurrently, live replication), OR
4. **Reliability**: a single SQLite DB file corruption/restore event in prod
   (WAL on shared NFS-backed storage is the known corruption risk), OR
5. **Strategic**: KRTaker lands a second client deployment needing multi-tenant
   isolation guarantees beyond the current API-level scoping (RLS becomes the
   hard backstop).

Until a trigger fires: **STAY on SQLite**. It's fast, zero-ops, and the
busy_timeout/WAL config is adequate for the current single-box, low-concurrency
profile. Do NOT pre-migrate — carrying two DB backends in the API is real cost
with no payoff at this scale.

## Staged plan (when a trigger fires — ~4–6 hours total)
- **Stage 0 — Preflight (30 min)**: export live DB via superadmin `app-export`
  (JSON) + `app-backup` (binary snapshot). Verify export row counts vs live
  counts per table. Snapshot + tag the repo.
- **Stage 1 — Provision (45 min)**: VPS (t3.small+ if cheap, else existing
  Lightsail once SSH unlocked) → install PG 14+ → create `krtaker` DB + roles
  (`krtaker_app` NOLOGIN, `krtaker_staff` BYPASSRLS) → run `pg-migration.sql`.
- **Stage 2 — Import (30 min)**: `pg_import.py export.json --dsn ...` →
  verify row counts match export; spot-check RLS recipe from
  `references/pg-migration.md` (cross-org isolation proof).
- **Stage 3 — API switch (1–2 h)**: in the API's `db()` (lib_core), branch on
  env `DB_DRIVER=sqlite|pgsql` — PDO DSN + a `q()` abstraction that maps
  SQLite-specific SQL (`INSERT OR IGNORE`, `datetime('now')`, `LIMIT ? OFFSET ?`,
  `AUTOINCREMENT`) to PG equivalents. Keep the SQLite path as fallback during
  the cutover window. Deploy to a **staging subdomain** first (test.krtaker.com
  pattern), run the 53-suite rig against the PG-backed API (add a PG mode to
  the harness), then flip prod behind a maintenance page.
- **Stage 4 — RLS activation (30 min)**: enable FORCE RLS + set
  `app.current_tenant` after every auth check (pooled-connection reset rule).
  Verify superadmin still sees all (BYPASSRLS), cross-org INSERT blocked.
- **Stage 5 — Cutover + rollback (45 min)**: switch env, warm, monitor
  app_error_log for 24h. Rollback = flip env back to SQLite (DB snapshot kept).

## What stays the same after migration
- UAPI/FTP deploy pipeline unchanged (PHP still runs on cPanel; PG lives on
  the VPS, reachable over network once SSH/security-group opened).
- Frontend (static HTML + dashboard-v2.html) untouched — API contract stable.
- The 53-suite rig remains the gate; a PG mode is added to it in Stage 3.

## Owners / blockers
- **Blocker**: VPS SSH access (18.142.98.150) — existing keys denied. Need the
  box pubkey or the Lightsail .pem, OR provision a fresh VPS (option A of the
  ERPNext decision could double as the PG host — one box, two services).
- Decision made; execution waits on the trigger or the SSH unlock, whichever
  comes first.
